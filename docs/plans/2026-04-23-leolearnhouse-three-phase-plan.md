# LeoLearnHouse 三阶段拆解方案

## 1. 项目本质判断

从代码结构看，LearnHouse 不是一个单纯的 LMS 前台，而是一套覆盖“内容生产、内容分发、学习行为、协作编辑、运维部署”的完整平台。

它当前至少包含四层：

1. 产品层：课程、章节、学习页、用户、组织、讨论、合集、证书
2. 创作层：Notion-like 编辑器、嵌入式内容块、代码块、媒体内容
3. 平台层：实时协作、AI、分析、Webhook、搜索、支付、对象存储
4. 运维层：CLI、自托管、Docker Compose、反向代理、健康检查、备份恢复

如果目标是“做自己的产品”，那就不能把这四层同时启动。最合理的做法是先只做产品层，再逐步引入平台层和运维层增强。

## 2. 哪些属于核心，哪些属于臃肿

### 2.1 真正的核心

这些能力决定产品是否能形成最小闭环：

- 用户认证
- 管理后台
- 课程结构
- 内容展示
- 学习进度
- 组织基础设置
- 媒体上传

### 2.2 当前阶段可以视为“臃肿”的部分

这些不是没价值，而是对于第一版你自己的产品来说，不应该先做：

- `apps/collab` 实时协作服务
- `apps/api/src/services/ai` 与 `apps/api/src/routers/ai`
- `apps/api/src/services/analytics`
- `apps/api/ee` 与 `apps/web/ee`
- boards / playgrounds / podcasts
- 支付和企业版接入
- 多组织、多租户、SSO、SCORM
- 官方 CLI 的完整部署与运维能力

## 3. 三阶段实施建议

### 阶段一：先做最小教学闭环

目标：做出能让老师创建课程、让学生完成学习的第一版产品。

建议保留：

- Web 前端里的登录、后台、课程相关页面
- API 里的 auth、users、courses、orgs、media、health 等基础能力
- PostgreSQL 作为主库
- 必要时保留 Redis，但如果你后续重构，第一阶段可以尽量减少对 Redis 的强依赖

建议砍掉或先不接：

- Collab
- AI
- Analytics
- Boards
- Playgrounds
- Podcasts
- Payments
- SSO / SCORM / EE 能力

产出目标：

- 管理员可以创建站点
- 教师可以创建课程、章节、课时
- 学员可以登录、浏览、学习、看到进度
- 能上传封面、附件或视频链接
- 整体页面和文案已经换成你自己的品牌

为什么这样拆最合适：

- 功能闭环清晰
- 研发成本最低
- 最容易验证市场反馈
- 本地和服务器成本都最低

### 阶段二：补商业化和运营能力

目标：让系统从“能用”进入“能经营”。

建议加入：

- 用户组、班级、角色细化
- 课程合集、学习路径
- 评论 / 讨论
- 邮件通知
- 基础数据面板
- 完成证书
- 付费课程或订单能力

阶段二重点：

- 完善增长、转化、留存相关功能
- 明确哪些能力必须依赖外部服务
- 开始建立更稳定的部署方式

这一阶段的关键不是技术炫技，而是让产品开始像一个真正可以运营的业务系统。

### 阶段三：再做平台能力

目标：当业务已经证明需要时，再引入高复杂度系统。

适合进入阶段三的功能：

- 多人实时协作文档
- 白板
- AI 助教 / AI 内容生成
- 高级分析
- 多组织 / 多租户
- SSO / 企业能力
- 高级集成与开放平台

阶段三为什么必须后置：

- 每一项都显著提升研发和运维复杂度
- 会增加更多外部服务依赖
- 会拉高排错难度、测试成本和服务器成本

## 4. 本地开发可行性评估

### 阶段一

非常可行。你现在的机器只要能稳定跑：

- Docker
- PostgreSQL 容器
- Redis 容器
- Node/Bun
- Python

就可以支撑第一阶段开发。即使后续你做裁剪版，第一阶段也完全可以在一台本地开发机上持续推进。

### 阶段二

仍然可行，但会开始受这些因素影响：

- 邮件服务配置
- 对象存储配置
- 第三方登录或支付联调
- 数据迁移和配置管理

### 阶段三

本地不是不能跑，而是会开始“跑得起来但不好维护”：

- 更多服务并发运行
- 更多长连接与状态同步
- 更多需要真实环境才能验证的问题

## 5. 服务器建议

### 阶段一

适合：

- 单台云主机
- Docker Compose
- 应用和数据库同机，先追求简单

建议配置：

- 2 vCPU
- 4GB RAM 起步，最好 8GB
- 40GB SSD

适用场景：

- 内测
- 小规模试运营
- 产品验证

### 阶段二

适合：

- 应用容器与数据库分离
- Redis 独立
- 对象存储外置
- 邮件服务外置

建议配置：

- 4 vCPU
- 8-16GB RAM
- 80GB SSD

适用场景：

- 稳定对外使用
- 小团队协作
- 有真实用户和内容增长

### 阶段三

适合：

- 分层部署
- 独立数据库
- 独立 Redis
- 独立协作服务
- 更完整的监控、日志、备份、CDN 与安全策略

建议配置：

- 8 vCPU 起
- 16-32GB RAM
- 按内容量和访问量规划存储

适用场景：

- 多租户
- 协作密集
- AI 与内容生产并重
- 企业客户场景

## 6. 我对你最推荐的执行顺序

1. 先把仓库定位从“上游克隆”改成“我的项目研究与演进仓库”
2. 先做品牌替换和 README 重写
3. 再列一份第一阶段必须保留的模块白名单
4. 基于白名单跑通本地开发环境
5. 只围绕第一阶段做页面和后端裁剪
6. 等第一阶段稳定后，再评估第二阶段

## 7. 现阶段最重要的判断

如果你的目标是尽快做出自己的产品，那么最优策略不是“把 LearnHouse 全部学完再动手”，而是：

- 先理解它的骨架
- 再确定你自己的最小产品边界
- 最后只搬运与你目标强相关的 20% 核心能力

这会比全量继承上游更快，也更适合长期维护。
